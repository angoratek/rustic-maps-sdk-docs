Rustic Maps SDK

Rust API reference

Generated from the SDK contract and the Rust crate sources. Do not edit this page by hand; change the sources and regenerate the documentation.

The Rust libraries give you the map SDK engine without a platform view: the projection and camera math, the overlay and tile pipeline, provider contracts and their registry, offline routing over compiled archives, and the turn-by-turn navigation core. The same code backs the Android, iOS, React Native and WebAssembly surfaces. This page indexes the public modules and items of the five libraries and carries their documentation comments; the generated Rust documentation carries the full signatures and examples.

Naming and conventions

  • Types are PascalCase, functions and methods are snake_case, and record fields are snake_case.
  • Records are plain Debug + Clone + PartialEq values; none carries a handle or a lock.
  • Provider traits are asynchronous and return Result<_, SDKError>; a provider never panics across the seam.
  • MapCamera and the camera transforms are pure values. Shared state lives behind Arc and short locks.
  • Listener callbacks run on the dispatching thread and must not block; re-entrant dispatch is suppressed by the single-in-flight guard.
  • The GPU renderers are native-only; the WebAssembly target uses the canvas renderer, which shares the camera, scheduler and overlay types.

Module blocking_work

The executor seam for blocking work.

Some SDK work is synchronous by nature: the response store that backs the cache-then-network policy reads and writes SQLite, and the offline routing engine runs a CPU-bound graph search. Running either on the async reactor monopolizes the thread that drives every other future.

[BlockingWorkExecutor] is the seam that moves such a job to where blocking is acceptable. A target with worker threads (the native bindings) implements it over a blocking thread pool; a target without threads (the browser) uses [InlineBlockingWorkExecutor], which runs the job where it is awaited. The cache and routing layers depend only on the trait, so neither names an executor implementation.

Module offline_routing

Offline route calculation over compiled routing graph archives.

[ArchiveOfflineRoutingProvider] implements [OfflineRoutingProvider] over a compiled routing graph archive. It loads the archive from a memory-mapped file on native targets or from in-memory bytes on every target, validates it with the archive reader, and builds the adjacency and turn-restriction indexes once. Route requests are then answered with A* under a haversine heuristic.

Targets

The whole module compiles on every target; only graph loading differs.

  • [OfflineGraphSource::Memory] is available everywhere and is the only graph source on WebAssembly. - [OfflineGraphSource::FilePath] memory-maps the archive on native targets. On WebAssembly it returns [SDKError::ProviderRequestRejected] with a message that directs the caller to [OfflineGraphSource::Memory], because the browser has no memory mapping.

Routing behavior

  • Only automobile routing is supported. The archive carries an automobile profile, so a request for another transportation mode is rejected with [SDKError::ProviderRequestRejected] rather than answered. - Costs follow [RouteOptions::route_strategy]: Fastest minimizes edge durations and Shortest minimizes edge distances. Edge speeds and road classes come from each edge record. - Steps are derived from graph metadata. Besides road-class and speed runs, a step boundary occurs at every junction whose signed bearing change leaves the straight band; the step then carries the matching [TurnDirection]. A road-class or speed change without a turn produces a Continue step. The archive carries no street names, so instruction text stays name-free and faithful to the geometry, for example "Turn right" or "U-turn". A strongly curved road yields a step at each junction. - Display and speech text on a step names the maneuver at the step’s end junction, the point a countdown to the next maneuver refers to. [ManeuverType] stays anchored to the maneuver that opens the step. See end_anchored_instruction_text. - Turn restrictions are evaluated against the incoming edge of the settled path. The approximation is exact unless a node is reachable through several best-cost paths with differently restricted incoming edges; in that case it can over-restrict, never under-restrict.

Threading and async

[OfflineRoutingProvider::load_offline_graph] validates the archive and builds the graph indexes, and [OfflineRoutingProvider::calculate_offline_route] snaps the endpoints and runs A*. Both are CPU-bound and run through the blocking-work seam ([crate::blocking_work::BlockingWorkExecutor]): a target with a blocking pool runs them on a worker thread, and the browser runs them inline on its single task queue. No lock is held across an await; the search clones the loaded graph handle and releases the read lock before running.

A load validates the new archive completely before replacing the current graph; a failed load leaves the previous graph loaded. The provider is safe to share across threads.

Search engine and performance measurement

[a_star_search] and [dijkstra_reference_search] expose the search engine directly so performance can be measured over the same loaded graph. Dijkstra is a reference baseline only: production routing always goes through A*. Both searches expose [ComputedRoute::settled_node_count], a deterministic expansion metric for comparing them. These items are hidden from generated documentation and are not part of the supported API.

Module provider_observation

Provider-request observation: the record a console shows for one provider call, and the sink the SDK installs to receive it.

The observation is built here rather than in a provider crate so the redaction rule has one home: a request path keeps its structure, query values are dropped except the documented non-secret parameters, and the response snippet is capped at [RESPONSE_SNIPPET_MAXIMUM_BYTES] on a character boundary. A credential reaches this module as part of the request and never leaves it — the tests feed one through a request and assert the observation carries neither the value nor the parameter pair.

The sink is process-wide because the provider crates are stateless with respect to the SDK: the native binding and the browser façade each install one observer at startup, and a provider crate used on its own (a unit test, a stand-alone integration) runs with none installed and pays no cost.

Module traffic_flow_cache

Grid-keyed, memory-bounded caching of traffic-flow observations.

A traffic layer asks its provider for the segments inside a camera’s bounding box every time the camera settles. The provider answers for a region, and the region a camera shows changes by a few pixels on every small pan, so a cache keyed by the exact requested box would miss almost every time. This module keys cached answers by the web-mercator tile grid instead: a request is answered from the cells it covers when those cells are fresh, the missing cells are fetched from the provider once as their union, and the provider’s answer is stored per cell. A pan of a few pixels is therefore a hit, a revisit of an earlier area is a hit, and memory stays bounded by a fixed entry budget with least-recently-used eviction.

An answer is the segments the covering cells hold — what the provider reported for that ground — not a re-filtered subset of it. A cell is coarser than a camera, so a hit can hold a few segments just outside the requested box; the renderer clips those at draw time, and narrowing them here would drop observations a provider chose to report.

The clock is injected ([TrafficFlowCurrentTimeSeconds]) rather than read from the platform: the crate compiles for the browser, where the standard library’s clock panics, so the host supplies its own (the browser target uses Date.now(), the native targets SystemTime). Tests supply a controllable clock.

The cache never holds a lock across an await: a request inspects the cells under the lock, drops it, awaits the provider, then re-takes the lock to store the answer.

Module geojson_source

Deterministic GeoJSON tiling at the source boundary.

A GeoJSON source is consumed through this module so downstream buckets, overlays and symbol placement see the same [VectorTile] feature model a vector source produces. The tiler projects each GeoJSON position through web mercator into tile-local extent coordinates, clips it to the tile rectangle, optionally simplifies it and quantizes it to the integer extent.

Tiling policy

  • Projection: longitude and latitude convert to normalized world coordinates, then to the tile’s local grid of [DEFAULT_TILE_EXTENT] units. - Clipping: points outside the tile (plus the configured buffer) are dropped; line segments are clipped to the rectangle; polygon rings are clipped with the Sutherland–Hodgman algorithm and re-oriented so an exterior ring winds positively and a hole negatively in the tile’s (x right, y down) grid. - Simplification: the Douglas–Peucker algorithm runs on the tile-local float geometry with the configured tolerance. The default tolerance is zero, so quantization to the integer extent is the only loss. - Quantization: every surviving coordinate rounds to the nearest integer extent unit, consecutive duplicates collapse, rings with fewer than three distinct vertices drop and line pieces with fewer than two drop. - Determinism: features keep their input order, attributes sort by key, polygon rings keep their source order with each exterior followed by its holes, and a generated feature id is a fixed FNV-1a hash of the feature’s canonical JSON. The same collection and the same tile address therefore always produce a byte-identical tile.

The module is pure CPU and JSON: it never fetches, reads a clock or uses a hash map whose iteration order could leak into the output.

Module headless

Headless wgpu rendering of raster tiles plus deterministic frame capture.

The renderer draws one textured quad per pooled tile for a single frame into an off-screen render-attachment texture and reads the pixels back into a [CapturedFrame]; an optional overlay layer ([crate::overlay::MapOverlay]) draws after the quads in the same render pass through a separate solid-color pipeline. Pooled payloads that fail to decode are skipped for the frame and evicted from the pool so the scheduler refetches them: one corrupt tile never poisons the frames after it. Only structural failures (an overflowing draw list, a failed context acquisition or capture) are errors. No window surface is requested, so this works on any native backend (Metal, Vulkan, DirectX). Device acquisition lives behind the object-safe [GraphicsContextSource] trait, which keeps wgpu types out of the scheduling core and lets a caller substitute its own context source or skip rendering when no adapter exists.

This module is native-only: it blocks on the asynchronous wgpu initialization calls and polls the device, which is not valid on WebAssembly, where the browser’s own async runtime drives WebGPU.

Capturing snapshots

A capture composes the scene into an off-screen render attachment that is never presented to a window, and [capture_frame_bytes] reads the result back. The readback is inherently blocking ([capture_frame_bytes] escalates to a blocking device poll).

For deterministic captures, [HeadlessTileRenderer::snapshot_frame_when_idle] refuses to render while pending tile work remains, returning [HeadlessRenderError::PendingTileWork] immediately without touching the GPU; otherwise it behaves exactly like the ordinary capture. The refusal decision costs no device work and never waits for pending work to finish. Completing that work is the caller’s next prepare frame. [HeadlessTileRenderer::render_captured_frame_with_overlays] is the ungated form: it always renders and captures, however much tile work is still pending.

The idle gate covers tile fetch state only; camera animations are composed outside this renderer entirely (see [crate::tile_scheduler] on the full idle semantics).

Module labels

The frame-level label pass: symbol-layer text from decoded vector tiles becomes screen-space glyph quads, anchored at a point for place and POI names and run along a line for road names.

The pass is deliberately GPU-free, like the overlay assembly: the native headless renderer, the native surface and the browser canvas all call the same functions and upload the same vertices, so the backends cannot drift in where a label lands or which labels survive.

Three stages:

  1. [label_candidates_for_vector_tile] walks a decoded tile’s symbol-layer features and reads each label’s text through the compiled style’s text-field expression. Candidates keep the style’s paint, size, priority, rank, placement and overlap rule. A symbol layer’s filter also gates a feature before it becomes a candidate: the converted styles encode the zoom-stepped rank ceiling and the per-class minimum zooms as step expressions on ["zoom"] inside an all filter. A [SymbolPlacement::Point] layer anchors a candidate at each of the feature’s points; a [SymbolPlacement::Line] layer carries the feature’s whole line geometry so the frame can place the text along it. 2. [LabelLayer::place] projects the candidates through the frame camera, thins them by rank at the frame zoom, sorts them by symbol class, then feature rank, then style-layer order (the documented collision-priority rule: lower priority is more important), and greedily rejects any label whose padded glyph box intersects a label already placed. Every drawn glyph contributes its own box, so a name can sit in the gap beside a neighbour’s word space; a rotated line label tests its oriented boxes. allow_overlap labels skip the test and never block later labels. The frame places at most [MAXIMUM_LABELS_PER_FRAME] labels: once that budget is spent, every remaining candidate is dropped even if it would fit, so a dense downtown cannot out-shout the places that matter. A share of the budget is kept free for line-placed names ([RESERVED_LINE_LABEL_SLOTS]), so a frame whose ranked places would spend the whole budget still carries street names. A label whose text repeats an already-placed label is dropped, so the buffered overlap between adjacent tiles cannot paint one place twice. The output order is a pure function of the input order and the camera, unless the caller hands the previous frame’s placed labels to [LabelLayer::place_with_history]: among candidates that tie on the priority key, a name the previous frame placed is tried first, so a panning frame holds a name on screen instead of letting an equal-priority newcomer take its space on one frame and lose it on the next. History never reorders across symbol class, rank or style-layer tier, so the frame stays a deterministic priority order.

A line-placed label projects its geometry and takes its longest straight run (consecutive near-collinear segments) as the text’s run: the text is centered halfway along that run, rotated to its chord bearing, flipped so it always reads upright, and skipped when the run is shorter than the text plus the collision padding at each end. Each glyph’s collision box takes the label’s rotation, so a road name rejects with its oriented extent, not the empty corners of an axis-aligned bound. 3. [LabelLayer::quad_vertices] lays the glyph bitmaps out on the atlas and emits clip-space textured quads, halo first and text second. A rotated label rotates each glyph’s screen-space rectangle about the label’s anchor before converting it to clip space, so every backend that draws these vertices carries rotation without a second vertex format.

Latin text is measured from the decoded glyph ranges and nothing here shapes complex scripts (see rustic-maps-glyphs). A frame with no symbol layers or no glyphs produces no vertices, so the tiles-only pipelines stay byte-identical.

Module legacy_vector_style

Vector-tile styling: a decoded [rustic_maps_vector_tiles::VectorTile] becomes the renderer’s overlay primitives — filled polygons for polygon features, polylines for line features, point markers for point features — under a small explicit style.

The style is deliberately data-only: a layer entry names the source layer, the geometry kind it paints, an optional one-attribute text filter and the paint values (RGBA, line width, marker radius). A symbol layer declares the label style a text pass will use — ordered text-field fallbacks, font stack, size stops, text and halo paint, [VectorSymbolPlacement], priority and overlap — but paints no overlay primitive itself: the frame-level label pass ([crate::labels]) reads it and draws its text through the glyph atlas, either anchored at a point or run along a line feature. The style carries no expression language. The artifact [DEFAULT_VECTOR_STYLE_ARTIFACT_JSON] carries the default style; [default_vector_tile_style] parses it and [in_code_default_vector_tile_style] is the documented fallback when the artifact is missing or malformed.

Polygon features paint every exterior ring with its interior rings subtracted through the overlay’s hole-aware fill (see [crate::overlay::FilledPolygonOverlay]), and the conversion groups its primitives into one [VectorOverlayBatch] per style layer, which a dedicated vector pipeline can consume.

Coordinates convert from tile-local extent space (x right, y down, the MVT convention) through the tile’s web-mercator address to geographic degrees, so the overlays project exactly like every other map coordinate.

Module location_indicator

GPU-free location-indicator assembly: the position fix drawn as a screen-facing two-mode puck over its optional ground-projected accuracy ring, in the same clip-space stream pattern the overlay layer uses (see [crate::overlay]).

The indicator is the third draw layer of a frame — the explicit draw order is tiles, then overlays, then the indicator ([LOCATION_INDICATOR_TOP_LAYER_DRAW_ORDER]) — so the fix’s visuals always paint over route lines and polygons without the overlay list growing or reordering. The vertices reuse the [crate::overlay::ClipSpaceOverlayVertex] type and draw through the existing overlay solid-color pipeline (a shader/layout-identical third pass), alpha-blended over what the first two layers drew.

The puck has two modes:

  • Tracking mode ([LocationIndicatorVisualKind::TrackingDot], or a fix without a course): a soft dot — an accent core disc, a white ring around it, and a subtle dark halo under both for legibility on light and dark maps. * Navigation mode ([LocationIndicatorVisualKind::GuidedCourseArrow] with a reported course): an up-course dart with a white outline and the accent fill inside the same white ring and halo, rotating with the course. Without a course the navigation form degrades to the tracking dot.

Layer semantics:

  • Screen anchoring. The puck is a screen-space shape anchored at the fix’s projected position — the fix’s pixel stays fixed under zoom and pan while the layers beneath move, exactly like point markers do (center anchoring, “screen-facing”). At pitch this keeps the puck legible where a ground-projected dot would foreshorten to a sliver, and the dart rotates with the camera’s bearing so a course heading reads as the same compass direction it reads on the ground. * Accuracy ring. A ground-projected circle of the fix’s horizontal accuracy — the honest reading of “this fix is this accurate” — drawn through the filled-polygon machinery, so it foreshortens into the ellipse the ground shows at pitch and splits at world-copy boundaries like every other ground shape. A fix more accurate than [MINIMUM_ACCURACY_RING_DRAW_METERS] draws no ring (a circle inside the puck itself carries no information), and an absurdly coarse fix clamps to [MAXIMUM_ACCURACY_RING_DIAMETER_PIXELS] on screen instead of flooding the viewport. * World copies. The screen-facing shapes anchor once per visible world-copy window like the tile spans’ fragments, so at the zoom < 1 world-copy views the indicator draws in every copy that renders the fix; the ground ring splits across windows in the polygon machinery. * Behind the camera. A screen-shape anchor whose homogeneous weight is not positive (the fix behind the camera plane) draws no puck — the screen-space shapes’ documented skip — while the ground-projected ring still projects by genuine corners and leaves near-plane straddling to the GPU’s frustum clip.

Module overlay

GPU-free overlay assembly: route polylines, filled polygons, point markers, and traffic-flow lines projected into clip-space solid-color triangle lists drawn over the tile quads.

Overlays are the second draw layer of a captured frame: the same camera pose and viewport that assemble the tile quads ([crate::renderer::Renderer::frame_quads]) also project overlay shapes into clip-space triangles via [overlay_triangle_vertices], which the headless renderer draws through a separate solid-color pipeline in the same render pass after the tiles. The WebAssembly canvas mirrors the vertex contract verbatim, so the assembly here is deliberately wgpu-free and emits one flat, non-indexed triangle list.

Assembly semantics:

  • World copies / antimeridian. Overlay geometry wraps around the camera exactly like tile spans do (see [crate::renderer::FrameProjection]): the first vertex of a shape sits in the camera’s world copy via the shortest wrapped delta, every following vertex unwraps continuously from it, and each resulting segment or triangle is split against the camera-centered world-copy windows ([WORLD_COPY_WINDOW_OFFSETS], reusing the tile spans’ window half-width). A shape wider than the covered window range clips to nothing beyond it; a single unwrapping step never spans more than half a world, so three windows cover every reachable fragment. * Frustum clipping. Assembly relies on the GPU’s clip-space frustum clip, the same mechanism the tile pipeline relies on for near-plane straddling spans; no extra CPU cull runs. Screen-space-thickened shapes (route lines, markers, traffic) additionally drop the segments and markers with a vertex at or behind the camera because the screen-space width offset needs a positive homogeneous weight; filled polygons emit genuine clip-space corners and keep near-plane straddling triangles for the GPU to clip exactly. * Line joins. A polyline draws as butt-capped segment quads plus one screen-space square (the line’s width) per interior vertex, oriented along the bend’s bisector. The square fills the wedge the butt caps leave outside a bend, which otherwise reads as a gap between styled road segments; it never grows a miter spike at sharp angles. Endpoints keep their butt caps (a per-feature end has no neighbouring segment to join), and sharp joins can still show a sliver where the wedge exceeds the square; a full round-join fan would close that gap.

That default stroke is what a route line, a traffic flow and a style layer that declares no line presentation draw. A style layer that declares any of line-cap, line-join, line-dasharray, line-offset, line-gap-width or line-blur carries a [PolylineStroke] instead, and the assembly honours it: miter joins limited to twice the half width (a sharper corner falls back to bevel), bevel and round joins, butt, square and round caps, dash runs measured in line-width units, perpendicular offsets, two-band casings outside a gap, and a documented blur fringe painted under the core stroke. * Polygon holes. A filled polygon carries one outer ring and any number of hole rings. Holes join the outer boundary through the standard bridge-splicing step before ear clipping ([FilledPolygonOverlay] documents the algorithm), so the emitted triangle stream covers exactly the ring set’s even-odd interior: the overlay pipeline paints a flat triangle list with alpha blending and has no stencil test, so a hole must leave its region out of that list rather than erase it after the fact. * Markers. A marker is a regular-octagon triangle fan centered on the projected anchor point (center anchoring, not bottom pinning): the projected coordinate is the fan’s center, so a marker’s center sits exactly at its geographic position. Sprites and label callouts are drawn by other layers. * Pins. A pin is a teardrop anchored the other way: its tip sits on the projected coordinate and the circular head above it carries a hollow center. The teardrop is star-shaped around the head center, so the outline is one radial function of the angle and the hollow center is the annulus between that outline and an inner circle — again a plain triangle list, no erase pass.

Module prefetch

GPU-free predictive prefetch planning: the bounded tile set a caller warms ahead of motion so the pool covers the camera’s next poses.

The planner emits an ordered request list — the camera’s visible set at its tile zoom first, then the ring of tiles ahead along the bearing vector ([PREFETCH_RING_TILES] viewport-heights ahead), then a navigation route corridor’s tiles when navigation feeds one, then one coarser fallback zoom under everything ([PREFETCH_FALLBACK_ZOOM_BELOW] below the camera’s tile zoom) — deduplicated against the pool’s contents and an already-warming set, capped at [PREFETCH_MAXIMUM_CONCURRENT_FETCHES]. The list feeds [crate::tile_scheduler::TileScheduler::warm_tiles] or its detached [crate::tile_scheduler::TileScheduler::plan_warm_tiles] twin, whose own per-call budget keeps the concurrent fetches bounded.

The navigation-corridor entries keep exactly the road corridor warm, and the effect is visible through the frame statistics a caller collects.

Module renderer

GPU-free frame assembly: prepared tiles mapped to drawable quads.

The pure half of the renderer. A [Renderer] consumes the camera pose, the viewport, and the tiles the [crate::tile_scheduler::TileScheduler] prepared for the frame, and produces the list of textured quads to draw in normalized world coordinates, including parent-fallback quads for tiles that the texture pool does not hold.

Quads are projected into per-fragment clip-space vertex arrays: a world span is wrapped around the camera as one unit (never corner by corner) and split into at most one vertex array per world copy it reaches, so spans crossing the antimeridian render contiguously instead of tearing. Everything in this module is free of wgpu types, so the quad assembly, the fallback texture window math, and the clip-space projection of the quad corners are all unit-testable without a GPU.

Module surface

Surface rendering of raster tiles plus overlays onto a live native window: the same scene composition as the headless renderer, presented through a real wgpu::Surface.

The renderer draws one textured quad per pooled tile for a single frame and an optional overlay layer ([crate::overlay::MapOverlay]) after the quads in the same render pass — byte-for-byte the headless pipeline’s geometry and shaders (the private shader sources and encode helpers mirror [crate::headless], and the WebAssembly canvas follows the same pattern) — but the frame renders into the next acquired surface texture and is presented, not captured. The pipelines therefore target the surface’s negotiated format (for example Bgra8Unorm under Metal), unlike the headless capture’s fixed FRAME_TEXTURE_FORMAT; the negotiation happens once at construction from the documented preference list and every later configuration keeps it.

Lifecycle

Per-platform raw window handles lower into a [wgpu::SurfaceTargetUnsafe] outside this crate, which takes over from there — this module is platform-agnostic and never names a windowing backend:

  1. Wrap the unsafe target with [SurfaceRenderTarget::from_unsafe_target], which creates the wgpu::Instance and the 'static [wgpu::Surface] against it. The raw handle must stay valid for the surface’s whole lifetime; wgpu’s own validity rules apply (see [wgpu::SurfaceTargetUnsafe]). 2. Build the renderer with [SurfaceTileRenderer::new], acquiring the adapter/device/queue through the injected [SurfaceGraphicsContextSource] (production: [WgpuSurfaceGraphicsContextSource], which requests an adapter compatible with the surface, unlike the headless source). The surface format is negotiated here. 3. Size the render area explicitly with [SurfaceTileRenderer::configure_extent] — resize is a call, not an observation: only a configure changes the swap-chain extent. A zero extent is refused; an already-configured extent reconfigures only when the extent changes. 4. Draw every frame with [SurfaceTileRenderer::render_frame]; the frame’s viewport must match the configured extent exactly. A stale surface (window resized or torn down behind the renderer’s back) reconfigures once and retries the acquisition before failing. 5. Detach by dropping the renderer: the wgpu surface’s own release semantics are its drop behavior (wgpu 30 has no separate un-configure call), so the host’s surface view drops the renderer — and every [SurfaceRenderTarget] it wraps — when its window handle goes away.

Attaching and detaching the underlying platform view belong to the caller. Dropping the [SurfaceRenderTarget] while its raw handle is reused elsewhere is a caller error to avoid, so the host code that owns the view must outlive the renderer.

Native only

Like [crate::headless], this module blocks on the asynchronous wgpu initialization and configuration calls (pollster) and is not valid on WebAssembly, where the browser runtime drives WebGPU.

Module tile_scheduler

Frame-driven raster tile scheduling with parent fallback.

Each frame the scheduler receives the XYZ tiles the camera needs (usually from [crate::projection::tiles_covering] on the camera footprint). For every requested tile it reports one readiness:

  • Present — pooled at the requested zoom; * FallsBackTo — a nearest pooled ancestor stands in while the detailed tile loads or while its fetch failed, so the map blurs instead of flashing holes; * Unavailable — the provider rejected the tile this frame; a later frame may retry.

Fetches are deduplicated within a frame (one provider call per distinct tile), ordered most-detailed-first, and capped by the configured per-frame fetch budget; requests beyond the cap report Deferred.

The idle render-state signal

An idle state means no more tile loads remain, so a capture made then cannot race a late fetch. This module exposes render-state queries: [TileScheduler::is_idle] over the fetch state, and [prepared_frame_is_idle] over a captured frame’s readiness verdicts.

What counts as pending is stated over the fetch state, because the scheduler itself is frame-driven: [TileScheduler::prepare_frame] awaits every fetch it issues, so a fetch is never observable through this API mid-flight. The pending states are therefore exactly the readiness verdicts whose pixels a later successful frame can still change:

  • Deferred — the fetch budget spent; a later frame fetches the tile. * Unavailable — the provider rejected the tile; a later frame retries it. * FallsBackTo — a coarser ancestor covers the area while the detailed tile loads or its fetch failed; when the fetch lands, the area re-renders at its own detail level.

A frame is idle when every requested tile resolved Present: no scheduled work can change its pixels. An empty request set is idle by vacuity. Idle is a query, not an event: it can flip back to pending when the pool loses a requested payload — least-recently-used budget pressure, or the renderer evicting an undecodable payload after a draw — until the next prepare frame refetches it.

Explicitly not part of the verdict: camera animations (crate::camera::CameraAnimation), which are composed entirely outside the renderer; GPU upload state, which never spans calls on the headless render path because uploads happen synchronously inside one frame render (the WebAssembly canvas, in contrast, keeps browser fetches in flight across a render frame); and evictions of payloads the current request set does not ask for.

Synchronous resolve and detached warm fetches

The frame path never awaits the network: [TileScheduler::resolve_frame] answers every requested tile’s readiness from the pool’s current state alone (plus the in-flight warming set it reports as Deferred), purely synchronously, and the misses are fetched by [TileScheduler::warm_tiles] (or its detached twin [TileScheduler::plan_warm_tiles], whose [TileWarmTask] runs on the caller’s background runtime) so detail arrives in a later frame. The blocking [TileScheduler::prepare_frame] awaits every fetch it issues; both paths report the same readiness verdicts over the same pool.

Diagnostics emit per-frame resolve and warm events at the Debug level and per-tile fetch events at the Trace level under the tile_fetch target, behind the diagnostics severity gate.

Module vector_base

Shared vector-tile base pipeline: one scheduler that fetches a vector tileset through the [VectorTileProvider] trait, decodes each tile once, styles it, and answers the overlay primitives the frame draws beneath its own overlays.

Every target serves its vector base through this one implementation, so the native surfaces and the browser cannot drift in what a tile paints. The scheduler owns two caches:

  • Decoded tiles, keyed by the tile address: a tile’s bytes are fetched and decoded once and never again while it stays cached; a style change restyles the decoded tile instead of refetching it. - Styled geometry, keyed by the tile address, the style revision and the style’s zoom bucket: the style’s zoom span (min_zoom/max_zoom) and width stops are evaluated at the camera’s zoom level, so a camera pan across a width stop repaints the tile from the style it already carries — no refetch, no decode. The zoom level quantizes to [VECTOR_BASE_STYLE_ZOOM_QUANTIZATION_STEPS_PER_LEVEL] steps per level so a continuous zoom gesture cannot grow the styled cache without bound.

A tile that fails to fetch or decode does not fail the frame: the scheduler skips it, keeps painting the tiles that succeeded, and reports the failure in the frame’s counts and its last failure detail. The base map is one layer of a frame, never the frame’s reason to fail.

Latency: payload cache, deliberate prefetch, progressive draw

The camera-facing [VectorBaseScheduler::cached_frame] never waits on the network: it paints the decoded tiles the cache holds, reports the rest as pending or failed, and lets a detached prefetch fill the gaps. A missing tile whose ancestor is cached draws that ancestor at the same camera zoom (the raster path’s parent-fallback semantics), so a new area blurs in at coarse detail instead of flashing holes.

Fetched wire payloads additionally pass through a [rustic_maps_core::CachedResponseStore] keyed by the tileset’s source name and the tile address. The native surfaces install their disk store (TTL, LRU and quota), so a region browsed once survives the next session; the browser installs [VectorTileMemoryCache], the same policy in memory where no SQLite exists.

[VectorBaseScheduler::prefetch_missing_tiles] claims the visible misses; [VectorBaseScheduler::prefetch_ring_tiles] then claims the ring around the viewport (and the coarse parents that back a fallback) under a small budget. Both return cancellable detached futures: a dropped future releases its claims, so a scheduler that is replaced mid-fetch never strands a tile address as permanently in flight.

The scheduler is camera-agnostic: the caller lists the visible tile addresses (through MapCamera::visible_tile_keys or the page’s own grid) and names the camera’s zoom level; [VectorBaseScheduler::served_zoom_level] clamps that listing to the tileset’s declared zoom span.

Each resolved frame also carries the drawn tiles’ label candidates, read from the active style’s symbol layers. [VectorBaseFrame::label_layer] places them at a camera pose through the SDK’s embedded default glyph font, so every platform surface draws the same place names without a platform-specific asset. A frame without candidates yields None and costs the renderer nothing.

Module zoom_transition

Cross-fade between adjoining tile zoom levels.

A camera crossing half a zoom level replaces its whole requested tile set in one frame: the new level’s tiles are fetched from scratch while the old level’s pixels are no longer drawn, so the view flashes the background and then fills in tile by tile. This module keeps the previous level on screen instead: while the new level’s tiles arrive it draws the retired level over them at full opacity, and once enough of the new level is present it dissolves the retired level out over a short fade. The tiles are projected with the current camera, so the per-tile world spans scale them automatically as the zoom changes.

The surface session (native) and the canvas draw state (browser) each own one [ZoomTransition] and feed it every frame’s requested tile zoom level, its present-tile fraction and a monotonic timestamp.

rustic_maps_navigation

The crate is a pure event reducer: [reduce_navigation_event] maps [NavigationEvent]s onto a [NavigationSession] without touching the network, the clock or the GPU. Module course_filtering

Course filtering: how a position fix’s reported course becomes the trip’s reported course.

A coarse GNSS fix’s course over ground is often the least trustworthy field the fix carries — a momentary standstill or an urban canyon reads as an arbitrary bearing, while the trip’s own route line is a much stronger statement about the real direction of travel. The policy is chosen once per trip:

  • [CourseFiltering::Raw] reports the fix’s course verbatim — the tunnel or canyon exit hatch where a garbage route projection must not override a correct physical course. - [CourseFiltering::SnapToRoute] projects the course onto the route line: while the fix is not judged fully off route, the reported course is the bearing of the route line at the user’s snapped position — every materially disagreeing raw course is replaced in one step, and the course stops jittering against the very line the position was already snapped onto. Without a route line to trust (the fix did not snap, or the projected segment carries no direction), the fix’s own course remains the fallback, and an unreported course retains the trip’s previous course (the same degradation continuity the snapped position keeps).

The filtering is decided per trip, like the step-advance and deviation policies ([crate::reducer::NavigationEvent::StartTrip] carries it), and the reducer stamps every fix’s effective course into TripNavigationState::course_heading_degrees during the same position snap pass, so consumers (a course dart, a follow camera) read one course field instead of re-filtering raw courses per platform.

Module deviation

Deviation (off-route) detection, the second decision policy beside the [crate::step_advance] conditions.

A [DeviationDetector] is consulted by the reducer on every location update, with the measurements the reducer already computed. The live detector instance travels in NavigationSession beside the state, never inside the exported plain-data record.

Judgment semantics

The shipped detector is a pure per-fix predicate over the measured distance: a fix is off route when its distance to the remaining route line exceeds the configured threshold widened by the fix’s reported horizontal accuracy. Widening is deliberate: the accuracy radius is exactly the plausible gap between the raw fix and the truth, so a genuinely on-route position may legitimately read up to one accuracy radius away from the line. A widened allowance suppresses those false flags gracefully instead of failing abruptly at a hard gate. The measurement is taken against the remaining route line (the current step onward) rather than only the current step, so a lagging step — eager advance semantics, pauses at intersections — is never mistaken for a deviation.

Two grades

A fix beyond the allowance from the remaining route line is judged fully off route. A fix inside the remainder’s allowance but beyond the allowance from the current step’s own polyline projects onto a future step and is reported as [DeviationStatus::OffStepOnRoute] (“on route, wrong step”). A shortcut, a self-intersecting route, or a lagging step advance can all legitimately put a fix on a later step, so the wrong-step grade is guidance feedback: the reducer neither freezes on it nor asks for a reroute, and the step-advance condition (with a delayed condition, within the very fix that produced the grade, via the reducer’s multi-step advance loop) reconciles the step. Only [DeviationStatus::OffRoute] is the freezing grade.

Hysteresis

The shipped detector uses one threshold for both raising and clearing a deviation, so the flag can flicker around the allowance edge. Hysteresis (a wider clearance than detection, or a minimum off-route time) is not part of this detector.

The reducer’s contract with the detector, documented in [crate::reducer]: a fix without an accuracy report is never judged at all — it can neither raise nor clear a deviation.

Module geometry

Polyline snapping mathematics for route progress.

The navigation state machine repeatedly needs two measurements against the current step’s shape: the closest point on the polyline (the snapped position) and the distance from a raw position fix to the polyline (the same minimum the deviation detector consumes later). Both live here so the projection error is documented and tested in exactly one place.

Projection model

Each segment is projected into a local equirectangular plane around its own midpoint: a north/south offset of y meters becomes y / RADIUS radians of latitude and an east/west offset of x meters becomes x / (RADIUS * cos(reference_latitude)) radians of longitude. This is exact along the reference parallel and along meridians within the small-angle approximation; the residual grows with segment length and distance from the equator. For the road-scale segments a navigation step carries (well under 1 km) at inhabited latitudes the distortion is far below a meter, comfortably inside GNSS accuracy. The minimization over segments uses this planar space; the reported distance is then recomputed exactly with the haversine formula. Antimeridian-crossing shapes are not supported: longitudes are treated as a plain number line.

Module instruction

Runtime turn-by-turn instruction composition for an active trip.

[compose_navigation_instructions] is a pure function of the current [TripNavigationState] (whose route field supplies the provider-authored steps) plus a [UnitSystem]: it produces the plain-data [NavigationInstruction] payload a UI banner or a text-to-speech engine consumes. The record is deliberately serializable — no Arc, no trait objects — so it can cross a language boundary unchanged.

Provider text is never rewritten

The emitter performs no natural-language understanding and does not rephrase, summarize or spell-normalize the provider-authored instruction strings ([RouteStep::instruction_display_text] and [RouteStep::instruction_speech_text]). The only text it authors is the live distance prefix ("In 130 meters"), composed as "<prefix>, <provider text>". With no distance left the prefix disappears entirely and the payload is the provider text verbatim. Where the provider authored no text at all, the payload is the explicit [ManeuverInstructionText::Unavailable] state — nothing is invented to fill it. When only one of the two variants is empty, the other (still provider-authored) variant is reused for both channels rather than synthesizing text: choosing which authored string to speak is not authoring.

Off route: an explicit rerouting-required marker

While the phase is [NavigationPhase::OffRoute] the reducer freezes the whole projection, so the composed payload below the marker is the last on-route instruction, unchanged across successive deviating fixes. Rather than presenting that stale instruction as trustworthy guidance, the payload carries an explicit [NavigationInstruction::is_rerouting_required] marker; a UI uses it to swap the banner for a rerouting notice, and the marker clears as soon as the deviation lifts or a reroute replaces the route.

Off route: the frozen countdown is suppressed, not presented

A frozen projection has no trustworthy distance to the next maneuver: any countdown composed off it would read as live guidance measured from where the device is not. While the freezing (FullyOffRoute) grade holds, the active maneuver’s phrase is therefore the explicit [DistancePhrase::Suppressed] state — no magnitude is phrased and the distance prefix drops from both text channels — mirroring the [ManeuverInstructionText::Unavailable] posture of composing nothing rather than composing something false. The provider-authored text is carried verbatim beneath the rerouting-required marker exactly as before. A merely wrong-step grade (OffStepOnRoute) keeps counting down: its fix still projects onto the route line, so the measured distance is real.

Distance phrasing bands

[DistancePhrase] rounds the raw distance to a named, boundary-tested band so successive fixes phrase identically while a user walks the span (“In 130 meters” instead of “In 131 meters”, “In 127 meters”, …). The pinned bands, rounded half-up:

| Band | Metric | Imperial | |—|—|—| | Immediate | below 5 m (= half the near increment) | below 50 ft (= half the near increment) | | Near | below 100 m: nearest 10 m | below 1000 ft: nearest 100 ft | | Moderate | 100 m–1000 m: nearest 50 m | 1000 ft–1 mile: nearest 500 ft | | Far | 1 km and up: nearest 0.1 km | 1 mile and up: nearest 0.1 mile |

The immediate band exists because half-up rounding of a sub-increment distance would otherwise phrase a 4 m approach as “In 0 meters”.

Module observer

Per-topic observers over the navigation state machine.

The module registers listeners per topic behind one [NavigationStateChangeListener] trait, each subscription with an explicit [TopicSubscription::cancel], so a consumer subscribes to only what it needs and each subscription cancels exactly itself:

  • instructions (dispatch_* always): the composed [NavigationInstruction] payload of every dispatched state change, produced by [crate::instruction::compose_navigation_instructions]; - deviation status (on change): [DeviationStatusChange] as the detector’s judgment enters, deepens/updates or clears — the per-fix judgment stream, including measurement drift while the phase stays OffRoute; - phase (on transition): [NavigationPhaseChange] — one-shot transitions OffRoute entered/cleared, RerouteProvided applied, and Arrived.

Threading contract

Dispatch is synchronous and single-threaded by contract: callbacks run on the caller’s thread, in the dispatch’s own stack frame. A host that needs callbacks on another thread performs that hop itself. Cross-thread calls are data-race-free (the trait requires [Send] + [Sync]) and are at worst suppressed by the re-entrancy guard, but the ordering guarantee is stated for single-threaded use only.

Dispatch rules

  • No lock is held across listener callbacks. The registry lock is taken once to snapshot the (cheaply cloned) listener lists and released before the first callback runs, so a listener may freely call back into the broadcaster — including [TopicSubscription::cancel] — without deadlocking. - Delivery order: within a topic, strict registration order; across topics, instructions first, then deviation status, then phase. - One dispatch in flight. The deliberate re-entrancy bound: a dispatch that starts while another dispatch is still in flight — typically a listener driving the reducer and re-dispatching from its own callback — delivers nothing and reports [NavigationDispatchOutcome::SuppressedReentrant]. Nothing is queued (no unbounded growth, no re-entrant cascade): the state change behind a suppressed dispatch is never lost — it already happened in the reducer — but its broadcast is skipped, so a listener that re-dispatches must let the outer dispatch finish and dispatch again from the top level. The common listener shapes (recording, platform notification) are fully synchronous and unaffected. - Listener errors cannot poison the reducer. Listener methods return nothing, so there is no error channel by construction; the dispatch runs after the reducer has already produced its new state and only reads the state it is handed. A listener that panics propagates the panic to the dispatch caller and cannot corrupt the trip state or wedge the broadcaster: the in-flight guard releases on unwind. A host that must contain listener panics catches them at its callback boundary. - Snapshot semantics for cancel: a subscription cancelled during a dispatch may still receive that dispatch’s callbacks (the snapshot was taken before); cancellation is guaranteed for every dispatch started after cancel returns.

Module recorder

Opt-in navigation recording for field diagnostics and debugging.

A [NavigationRecorder] implements the per-topic [NavigationStateChangeListener] surface and additionally records the raw position fixes delivered to the reducer through an explicit [NavigationRecorder::record_location_fix] channel (the raw fixes are not a listener topic — the listener surface starts downstream of them). Every recording is stamped with a strictly increasing sequence number and, when the clock is available, an instant in seconds since the Unix epoch, and is kept in a bounded ring that silently drops its oldest entry once full. A recorder therefore never grows unbounded and never slows the trip down beyond one short locked section per recorded item.

Recording is opt-in: nothing records unless a consumer holds a recorder and subscribes it or feeds it fixes. Recording stops when the recorder is dropped from every subscription.

The drained entries are the plain-data payload types the other navigation modules emit.

Module reducer

The pure event reducer driving an active trip.

[reduce_navigation_event] maps one event onto the previous session and returns the next one; it has no I/O, no clock and no mutable globals, so every outcome is reproducible from the event history. The live [StepAdvanceCondition] and [DeviationDetector] instances travel through [NavigationSession], pairing state with its decision objects because they are swapped for their [StepAdvanceCondition::fresh_instance] (or [DeviationDetector::fresh_instance]) counterparts at reset points, and the exported [crate::state::TripNavigationState] must stay free of trait objects.

Reducer semantics

  • [NavigationEvent::StartTrip] flattens the route and reports the declared step values as remaining progress until the first fix arrives. - [NavigationEvent::LocationUpdated] is judged for deviation first: a fix the detector grades fully off route freezes the session — the snapped coordinate and progress stay at the last on-route values, and neither the step-advance condition is consulted nor the step advances. Deviating positions must not drive route progress. A fix graded off the current step but on the route ([DeviationGrade::OffStepOnRoute], a projection onto a future step) never freezes on its own: the grade is recorded in the state, the trip stays Navigating — no reroute request, instructions keep counting down — and the fix is then processed normally (the step-advance condition reconciles the step; a delayed condition does so within the very fix, via the multi-step advance loop below). A fix without an accuracy report is not judged at all: it can neither raise nor clear a deviation, because one threshold rule cannot conservatively decide both directions. A graded fix inside the allowance lifts an active deviation (an OffRoute trip recovering from the route line, or a lingering wrong-step grade clearing) and the update then proceeds normally (condition consulted, position snapped, progress recomputed). [crate::state::NavigationPhase::OffRoute] is therefore a pause the user may recover from by returning to the route, not a terminal state. - Arrival-aware advance: the condition consulted for a hop is not always the trip’s own. Once the remaining steps — counted with the current step itself included — shrink to the arrival window ([ARRIVAL_CONDITION_REMAINING_STEPS_BOUND]), a separately configured arrival step-advance condition is consulted instead (falling back to the trip’s own condition when none was configured, which preserves the behavior of every trip that has none). Arrival itself is reachable only through that final-step verdict: an Advance while on the final step cannot pop another step — it declares [NavigationPhase::Arrived] and breaks the loop ahead of any further consult, so neither the loop’s defensive bound nor a still advancing condition can walk past the route’s end. - The trip’s course-filtering policy stamps an effective course ([TripNavigationState::course_heading_degrees]) during each processed fix’s position snap; see [crate::course_filtering]. - One fix may advance through several steps: after each single-hop advance — which swaps in the fresh condition instance — the freshly computed inputs decide whether the same fix advances the next hop too. The loop is bounded by [MAXIMUM_STEP_ADVANCES_PER_FIX] and terminates by construction: a hop can end the trip only by arriving, and every other break is the condition’s Remain. - [NavigationEvent::RerouteProvided] rebuilds the session for the same trip from a fresh route. Route computation policy lives at the caller’s event source; the reducer stays policy-free and pure. See the event documentation for the route-anchoring contract it implies. - Updates after the phase is Arrived are ignored; reroutes offered to an arrived trip are ignored as well.

Module reroute

Reroute-recalculation hysteresis: the gates a reroute request must pass before it may begin.

A fully off-route excursion asks the integrator for a replacement route, but the request itself is an expensive asynchronous calculation that must not be spammed by jittery fixes. Three hysteresis gates stand between the signal and the request, plus their observable in-flight readback:

  • Request-in-flight gate. While one recalculation is still in flight, a new one is refused; the integrator settles the request (applies or abandons it) before the gates open again. - Cooldown. A new calculation waits out [ReroutePolicy::recalculation_cooldown_seconds] of wall clock since the last one began (a fix jittering in and out of the route within the cooldown window cannot fire repeated requests). - Movement threshold. A new calculation also waits until the raw position has moved at least [ReroutePolicy::recalculation_movement_meters] from the fix current at the last calculation’s beginning (Raw fixes, not the snapped position: a fully off-route trip freezes its snap, so a movement gate read off the snap could never be satisfied while it is most needed).

The gate is stateful and wall-clock driven, deliberately outside the reducer: the navigation reducer stays a pure, clock-free event function, and the controller holds the gate beside the session and evaluates it with the fix instant, as it does for [crate::speech::SpeechInstructionPlanner]. The caller supplies now to [RerouteRecalculationGate::begin_calculation], which also makes the gates deterministic in tests.

Module route_walk

Distance-parameterised traversal of a planned route’s own geometry.

A simulated trip must follow the polyline the visitor actually planned, not a fixed demo line. [RouteWalk] flattens a [RouteData]’s legs → steps → shapes into one traversal-order polyline, collapses duplicate and zero-length segments, accumulates great-circle distances, and answers a fix either at a travelled distance or at an elapsed time. Because the SDK carries no pacing policy, the caller supplies a [SimulatedTripPace].

Traversal model

  • Distances between consecutive kept vertices are great-circle haversine distances (the same mathematics as GeographicCoordinate). - Vertices closer than [MINIMUM_SEGMENT_LENGTH_METERS] to their predecessor are collapsed, so duplicated step boundaries and repeated shape points contribute no segment and no undefined bearing. - A position between two vertices is a linear interpolation in latitude and in antimeridian-unwrapped longitude. This matches how the route polyline is drawn; over road-scale segments the difference from a great-circle arc is far below a meter. - Segment bearings are the direction of travel along the active segment, in degrees clockwise from true north (0 = north, 90 = east). At an exact interior vertex the outgoing segment’s bearing wins; the final vertex reports the last segment’s bearing. - Longitudes are unwrapped across the antimeridian before interpolation and bearings are computed, then the resulting coordinate is wrapped back into [-180, 180] the way the rest of the SDK normalizes world longitudes. A route from 179.9° to −179.9° therefore traverses 0.2° eastward rather than 359.8° westward.

Both fix functions clamp their argument into the route’s parameter range instead of failing: a negative or NaN distance/time is the trip start, anything past the end is the final fix. [SimulatedTripFix::is_arrived] is then true exactly when the fix sits at the route’s final coordinate.

Module speech

Speech-instruction triggering: when a guidance line is newsworthy enough to speak.

The SDK stays out of synthesis and playback: this module only decides when a fix is worth a spoken line, and answers with the composed instruction payload’s verbatim speech text, never text this module authored. The decision reuses the display phrase’s existing distance bands, so a spoken “in 100 meters” can never disagree with the banner’s shown phrase: the thresholds below are the very bands [crate::instruction::DistancePhrase] rounds with.

Emission rules (the named behaviors)

  • Trigger bands are the distance-phrase bands. Fix N crossed below a band’s threshold (in meters) announces that band: metric 10 m, 100 m, 1 km and the immediate half-increment threshold; imperial 100 ft, 1 000 ft, 1 mile and the immediate threshold. Each band announces at most once per step, and only the strictest band crossed in one fix speaks: a fix that jumps two bands announces the nearer stage only. - Monotone per step. The band memory resets only on a step advance, so distance jitter over a threshold can never re-announce a band. - Minimum inter-utterance spacing. After any line, the next band-triggered line waits for [MINIMUM_INTER_UTTERANCE_SPACING_SECONDS]. The immediate band overrides it: a “turn now” stage always plays. - Minimum repeat distance. A ManeuverApproach line whose trigger distance lies within [MINIMUM_UTTERANCE_REPEAT_DISTANCE_METERS] of the previous emission’s trigger distance is suppressed: two turns announced from distances closer than this read as chatter instead of guidance. The planner does not chain “then”; the near band’s own silence is the honest fallback. - Transitions always speak. An off-route recovery and an arrival emit unconditionally (the composed payload’s verbatim text) — they are the guidance-resumed and you-have-arrived lines, not pacing candidates, and like every emission they refresh the spacing memory. - Every emission carries its identity. Each emitted [SpeechUtterance] is stamped with a fresh, strictly increasing [SpeechUtterance::utterance_id] at the single emission site, and the counter survives every reset — so identical text re-emitted is a new identity, and the platform speaker’s dedup and flush decisions stay keyed on its own queue state.

Module step_advance

Step-advance conditions.

A [StepAdvanceCondition] is a pure decision object consulted by the reducer on every location update. Conditions are passed into the reducer as Arc<dyn StepAdvanceCondition> parameters and never live inside the exported [TripNavigationState], which must stay plain data for a language binding.

The fresh-instance contract

[StepAdvanceCondition::fresh_instance] returns the same configuration with any internal state reset. The reducer swaps the active condition for fresh_instance() the moment it advances. This prevents a rapid double advance: a condition that tracks progress within a step (for example, one awaiting several consecutive fixes) would otherwise carry saturated internal state across the advance and immediately advance again on the next update. Stateless conditions can simply return a clone of themselves, but the contract is uniform so composite conditions can reset every nested condition recursively.

Combinators

[OrStepAdvanceCondition] and [AndStepAdvanceCondition] wrap two inner conditions and decide on their combined verdicts. Both consult every inner condition on every update (even when the outcome is already decided for And): a stateful inner condition must observe every update for its internal schedule to stay sound. fresh_instance rebuilds both inner conditions fresh, so the reducer’s whole-composite reset on advance also resets each child.
