§Panic containment at the FFI edges

The task of this module is one decision, written down once instead of forty times: what happens when a Rust panic reaches an FFI edge of this crate — and where the crate takes deliberate panics instead of hidden unwrap/expect calls.

§What UniFFI’s own scaffolding already contains (verified against the

pinned uniffi 0.32.2)

Every frame the foreign code enters goes through code UniFFI generated, and UniFFI generated it with a catch boundary already installed:

  • Exported synchronous frames (free functions, methods, constructors, object handle clone/free): the generated extern "C" wrapper bodies are ::uniffi::rust_call(call_status, || ...) (the proc-macro scaffolding of the export/export_for_udl paths, uniffi_macros export/scaffolding.rs and object.rs), and uniffi_core‘s ffi::rustcalls::rust_call_with_out_status wraps that closure in panic::catch_unwind. A caught panic becomes the call’s RustCallStatusCode::UnexpectedError (an “unexpected error” status the foreign bindings report as an unspecified failure, not a typed SdkError), with the panic message lowered into the status’ error buffer; the message lowering itself runs inside a second, deliberately defensive catch_unwind.
  • Exported [Async] frames: the exported FFI function does not hand the future to the foreign executor; rust_future_new wraps it in uniffi_core’s WrappedFuture, whose every poll runs inside try_rust_call (with AssertUnwindSafe, because a panicked future is never polled again). A poll panic completes the future with the same unexpected-error status, so the foreign await resolves — the handback never tears — instead of the panic tearing through the executor.
  • The crate-owned runtime handback ([crate::runtime::drive]): a panic in the spawned work is deliberately resurfaced on the poller, which is exactly the frame the per-poll boundary above catches ([crate::runtime::drive] documents this pairing). A panicking fire-and-forget task ([crate::runtime::spawn_detached]) never crosses any FFI edge at all: it dies on the crate-owned runtime’s worker thread.
  • Foreign callbacks invoked from Rust (the [Trait, WithForeign] contracts): a foreign implementation raising an exception (rather than throwing the contract’s SdkError) is not a Rust panic at all — the foreign vtable reports an unexpected status and uniffi_core’s LiftReturn machinery turns it into UnexpectedUniFFICallbackError, which panics the proxy call unless the contract’s error type converts it (crate::error::SdkError implements that From; see there). That panic, like every other panic inside an exported frame, is caught by the same scaffolding boundary. Callback contracts whose methods have no error channel (NavigationStateEventListener, SdkDiagnosticEventListener) can only take the panic route; that is fine for the same reason.

So: no Rust panic can unwind into foreign code over UniFFI’s edges. Adding our own catch_unwind wrappers at the exported entry points would be redundant containment; mapping a caught internal panic onto a typed SdkError variant would be dishonest — every variant names a cause (invalid render input, network request failed, …) and none of them truthfully names “an internal invariant broke”. The scaffolding’s UnexpectedError status is the contract’s honest report for that. The one honest typing addition is crate::error::SdkError’s conversion of a foreign provider implementation’s unexpected failure, which today (without it) degrades through a panic into the same untyped unexpected error.

§The remaining deliberate panics: unreachable internal invariants

A small class of failure modes in this crate cannot produce an SdkError without lying, and cannot happen without a bug in this crate’s own code: a mutex that is only ever held over documented panic-free regions is poisoned by an internal invariant breach, and an invariant whose value is provably established by validation a few lines earlier. For those, the helpers below take the panic out of the unwrap/expect shorthand and into a documented, named choice — a panic that the scaffolding boundary contains, so an internal bug degrades an exported call to an unexpected error instead of aborting the process or hiding behind a default value.

The workspace clippy config denies clippy::unwrap_used and clippy::expect_used for the crate’s non-test build (see lib.rs); the helpers here hold the crate’s only justifications.
