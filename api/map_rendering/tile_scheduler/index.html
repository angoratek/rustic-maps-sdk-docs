Module tile_scheduler 

Source
Expand description

Frame-driven raster tile scheduling with parent fallback.

Each frame the scheduler receives the XYZ tiles the camera needs (usually from crate::projection::tiles_covering on the camera footprint). For every requested tile it reports one readiness:

  • Present — pooled at the requested zoom;
  • FallsBackTo — a nearest pooled ancestor stands in while the detailed tile loads or while its fetch failed, so the map blurs instead of flashing holes;
  • Unavailable — the provider rejected the tile this frame; a later frame may retry.

Fetches are deduplicated within a frame (one provider call per distinct tile), ordered most-detailed-first, and capped by the configured per-frame fetch budget; requests beyond the cap report Deferred. Fetch overlap with GPU work and eviction-aware prioritization are deferred until the render loop measures upload timing.

§The idle render-state signal

GL JS’s idle event fires when no more tile loads and no animation work remain — the condition golden-image tests await before capturing, so a capture can never race a late fetch. This module exposes the equivalent render-state queries: TileScheduler::is_idle over the fetch state, and prepared_frame_is_idle over a captured frame’s readiness verdicts.

What counts as pending is stated over the fetch state, because the scheduler itself is frame-driven: TileScheduler::prepare_frame awaits every fetch it issues, so a fetch is never observable through this API mid-flight. The pending states are therefore exactly the readiness verdicts whose pixels a later successful frame can still change:

  • Deferred — the fetch budget spent; a later frame fetches the tile.
  • Unavailable — the provider rejected the tile; a later frame retries it.
  • FallsBackTo — a coarser ancestor covers the area while the detailed tile loads or its fetch failed; when the fetch lands, the area re-renders at its own detail level.

A frame is idle when every requested tile resolved Present: no scheduled work can change its pixels. An empty request set is idle by vacuity. Idle is a query, not an event: it can flip back to pending when the pool loses a requested payload — least-recently-used budget pressure, or the renderer evicting an undecodable payload after a draw — until the next prepare frame refetches it.

Explicitly not part of the verdict: camera animations (crate::camera::CameraAnimation), which are composed entirely outside the renderer; GPU upload state, which never spans calls on the headless render path (uploads happen synchronously inside one frame render; the wasm canvas, in contrast, keeps browser fetches in flight across a render frame — the mirror of this signal there is deferred to the canvas slice); and evictions of payloads the current request set does not ask for.

§The sync resolve / detached warm split

The frame path never awaits the network: TileScheduler::resolve_frame answers every requested tile’s readiness from the pool’s current state alone (plus the in-flight warming set it reports as Deferred), purely synchronously, and the misses are fetched by TileScheduler::warm_tiles (or its detached twin TileScheduler::plan_warm_tiles, whose TileWarmTask runs on the caller’s background runtime) so detail arrives in a later frame. The blocking TileScheduler::prepare_frame remains the await-everything reference behavior the tests and goldens pin; the split’s verdicts are the same taxonomy over the same pool.

The diagnostics: per-frame resolve and warm events emit at Debug and per-tile fetch events at Trace under the tile_fetch target, behind the diagnostics severity gate (see map-native-core’s diagnostics module).
