Tile-pack management (PRD FR-F): region selection, download into the same SQLite store the cache uses, per-region on-disk reporting and eviction.

§The coexistence model (pack tiles versus cache tiles)

A pack’s tiles live in the very same store — and under the very same fingerprints — the CachedRasterTileProvider writes ordinary cache entries under. The pack is bookkeeping over those entries:

  • At TilePackManager::prepare_tile_pack the pack record plus one membership row per planned tile fingerprint is written first, before any download; a membership row without an entry is inert and merely names a tile still to download.
  • The download itself runs through the cached provider pipeline, so a present tile is served from the store (never re-downloaded) and a missing tile is fetched by the wrapped provider and stored by the store’s ordinary write path.
  • While the pack record exists, its member fingerprints are excluded from the store’s least-recently-used eviction (sqlite_store): ordinary budget pressure cannot remove a packed tile, only the pack’s explicit TilePackManager::evict_tile_pack (or a member entry’s own time-to-live expiry) can.
  • Pack entries are subject to the same per-provider imagery ceiling as ordinary cache tiles (PRD §6.7, owner ruling 2026-10-28): the pack’s effective retention is the requested value — defaulting to the tiles category’s thirty days — clamped to the installed provider’s declared ceiling. The clamp is the round-11 settings ruling’s behavior: a request above the ceiling is accepted and stores at the ceiling, the compliance bound is what the cache retains, never how the call returns.

The scheduler and renderer stay untouched: packed tiles flow to a TileScheduler-like caller through the same registered cached provider slot as network-fetched tiles, and are indistinguishable there (the FR-D seam; pinned by the integration test under map-rendering).
