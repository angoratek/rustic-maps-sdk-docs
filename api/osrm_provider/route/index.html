OSRM route service implementation of geospatial_traits::RoutingProvider.

§Request shape

One request is GET {base_url}/route/v1/{profile}/{longitude},{latitude};… with overview=full, geometries=geojson, steps=true and, when the caller asks to avoid features, exclude set to the requested OSRM classes.

§Option mapping

  • TransportationMode::Automobile selects the driving profile, TransportationMode::Bicycle the cycling profile and TransportationMode::Pedestrian the walking profile.
  • AvoidOptions::toll_roads becomes toll, AvoidOptions::limited_access_highways becomes motorway, AvoidOptions::ferries becomes ferry and AvoidOptions::unpaved_roads becomes unpaved, joined in one exclude value.
  • geospatial_types::route::UnitSystem does not change the request: the route contract is always meters and seconds, which is also what OSRM returns.

§Options OSRM cannot express

These are documented rather than silently approximated:

  • geospatial_types::route::RouteStrategy has no route-service parameter. The deployed profile’s cost model fixes the ranking, so Fastest and Shortest produce the same request.
  • RouteOptions::departure_timestamp_seconds has no route-service parameter. The service routes for “now”, so a requested departure instant is not honored.
  • exclude classes must be declared by the deployed profile. Requesting a class the profile does not declare makes OSRM reject the request, which surfaces as SDKError::ProviderRequestRejected.
  • OSRM returns no human-readable instruction, so this provider authors display and speech text from the maneuver and road name, and it does not map OSRM intersection lane records.
  • OSRM has no ferry maneuver type. A step whose mode is ferry is classified as ManeuverType::Ferry before the maneuver-type table is consulted, so a ferry crossing keeps its own instruction instead of degrading to Continue.
