Inputs the reducer accepts for one active trip.

Variants§

§

StartTrip

Begin navigating the given route with the given advance strategy.

The condition and the deviation detector are supplied per trip (the reference’s controller receives them the same way) rather than through configuration, so changing either policy is an explicit event in the history.

Fields

§route: RouteData

The route to navigate.

§step_advance_condition: Arc<dyn StepAdvanceCondition>

The strategy deciding when to move between steps.

§deviation_detector: Arc<dyn DeviationDetector>

The strategy deciding when the trip is judged off route.

§

RerouteProvided

Replace the route of the active trip (a reroute).

This event is the caller’s answer to a detected deviation — or a proactive route swap. The remote-first, offline-fallback policy (ask a remote router for a replacement route, fall back to an offline graph) decides where the replacement comes from and lives at the integrator/event-source layer; the reducer only applies it, staying pure and policy-free.

§Anchoring contract

Self::RerouteProvided rebuilds the session exactly as Self::StartTrip does, so the replacement route must be authored to begin at the trip’s current snapped coordinate — which is where a reroute router anchors its request anyway. The reducer performs no trimming or re-ghosting of the new route’s geometry; if the anchoring contract is violated, the next graded fix will be judged against the remaining route line by the deviation detector (and would flag a deviation), so a mis-authored reroute is at worst flagged, never silently mis-projected.

The replacement advance condition must be fresh from the caller’s side; the reducer additionally rebuilds it via StepAdvanceCondition::fresh_instance as a defensive reset so a mid-schedule instance carried over from the old route cannot corrupt the new step sequence (the double-advance contract).
