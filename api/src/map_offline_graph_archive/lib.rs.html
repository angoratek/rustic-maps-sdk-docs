1//! The `OfflineRoutingNetworkGraph` archive format (milestone M7,
2//! `PRD.md` §4.6): the format's reader and writer home, viable on every
3//! SDK target.
4//!
5//! This crate is pure byte parsing and encoding with no platform-specific
6//! dependencies outside [`geospatial_types`], so it builds on native
7//! targets and on `wasm32-unknown-unknown` alike: [`archive`] carries the
8//! format constants, the packed record types, the deterministic writer
9//! and the fully validating in-memory reader
10//! ([`archive::OfflineRoutingNetworkGraph::from_bytes`]), and the native, memory-mapped
11//! consumption seam ([`mmap_reader`]) is cfg-gated to non-wasm targets
12//! because `mmap` does not exist in the browser path.
13//!
14//! The two load paths share the entire typed corruption model: the
15//! mmap-backed reader answers the same byte slices the in-memory reader
16//! consumes, so a route computed from mapped file bytes and one computed
17//! from in-memory bytes of the same archive are identical by construction.
18//!
19//! # Container format decision (recorded 2026-10-29, milestone M7 slice 1)
20//!
21//! `PRD.md` §4.6 specifies a *flatdata* archive. The `flatdata` Rust crate
22//! (crates.io `flatdata 0.5.8`, last published 2024-08-30) was evaluated
23//! first and rejected: its Rust code generation has no macro path — a
24//! `build.rs` must call `flatdata::generate`, which shells out to
25//! `python3`/`pip` at build time and installs `flatdata-generator==0.4.6`
26//! from PyPI into a virtualenv under `OUT_DIR` before running it. That makes
27//! every workspace build non-hermetic and dependent on the network and a
28//! third-party Python toolchain, which this repository's build and test
29//! isolation rules do not allow. Per the documented fallback in `PLAN.md` §3
30//! ("flatdata rust crate maintenance staleness"), this crate instead pins
31//! its own minimal flatbuffer container following the same schema: the resource
32//! names, record layout and validation semantics match the PRD's archive
33//! shape, in a single self-describing little-endian file that this crate
34//! both writes (deterministically) and reads back with typed corruption
35//! errors. Should the `flatdata` ecosystem recover a hermetic Rust
36//! code-generation path, the format versioning in [`archive`] is the seam
37//! for a byte-compatible migration.
38//!
39//! # Archive format (version 1)
40//!
41//! All integers are little-endian. The single-file layout is:
42//!
43//! ```text
44//! offset 0  ARCHIVE_MAGIC ("RMOG")                        4 bytes
45//! offset 4  format version (u32)                          4 bytes
46//! offset 8  table-of-contents entry count (u32)           4 bytes
47//! offset 12 table-of-contents entries, 48 bytes each:
48//!           resource name (32 ASCII bytes, NUL-padded) +
49//!           resource offset (u64) + resource byte length (u64)
50//! resources in canonical order (see the [`archive`] docs), each offset a
51//! multiple of 8; unnamed padding gaps of up to 7 bytes may separate them.
52//! ```
53//!
54//! Resources hold packed array-of-structs records — the GraphHopper-style
55//! encoded-value columns ([`archive::EDGE_RECORD_BYTES`]'s `encoded_value`:
56//! speed cells, road class, direction access) keep the routing hot path
57//! branch-free. Corruption anywhere fails typed: [`geospatial_types`]'s
58//! `SDKError::OfflineRoutingFailure` with
59//! `OfflineGraphInvalidReason::{ArchiveMalformed, VersionUnsupported,
60//! IndexOutOfRange}`.
61//!
62//! # Who produces and consumes this format
63//!
64//! - The `map-offline-graph-compiler` crate (the OpenStreetMap PBF →
65//!   archive compiler, a maintainer/CI tool that never ships inside the
66//!   SDK and stays native-only: its `osmpbf` dependency is not
67//!   wasm-viable) writes archives in this format and re-exports the
68//!   [`archive`] module for its own code, fixtures and tests.
69//! - The SDK's `map-core` `OfflineRoutingProvider` consumes archives
70//!   through this crate on every target: in-memory bytes (the
71//!   `OfflineGraphSource::Memory` seam, the wasm path) everywhere, and
72//!   [`mmap_reader`]'s mapped file path on native targets.
73
