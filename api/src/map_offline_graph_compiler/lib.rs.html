1//! Offline routing network graph compiler.
2//!
3//! This crate compiles OpenStreetMap (PBF) extracts into the binary
4//! `OfflineRoutingNetworkGraph` archive defined by `PRD.md` §4.6: nodes,
5//! directed edges with encoded speed/road-class/access columns, lane
6//! guidance, instruction strings with lookup indices, and turn restrictions.
7//! It is a maintainer/CI tool, never shipped inside the SDK: the SDK itself
8//! only ever reads compiled archives (see the planned mmap reader and the
9//! `OfflineRoutingProvider` implementation, milestone M7 slice 2).
10//!
11//! # Container format decision (recorded 2026-10-29, milestone M7 slice 1)
12//!
13//! `PRD.md` §4.6 specifies a *flatdata* archive. The `flatdata` Rust crate
14//! (crates.io `flatdata 0.5.8`, last published 2024-08-30) was evaluated
15//! first and rejected: its Rust code generation has no macro path — a
16//! `build.rs` must call `flatdata::generate`, which shells out to
17//! `python3`/`pip` at build time and installs `flatdata-generator==0.4.6`
18//! from PyPI into a virtualenv under `OUT_DIR` before running it. That makes
19//! every workspace build non-hermetic and dependent on the network and a
20//! third-party Python toolchain, which this repository's build and test
21//! isolation rules do not allow. Per the documented fallback in `PLAN.md` §3
22//! ("flatdata rust crate maintenance staleness"), this crate instead pins its
23//! own minimal flatbuffer container following the same schema: the resource
24//! names, record layout and validation semantics match the PRD's archive
25//! shape, in a single self-describing little-endian file that this crate
26//! both writes (deterministically) and reads back with typed corruption
27//! errors. Should the `flatdata` ecosystem recover a hermetic Rust
28//! code-generation path, the format versioning in [`archive`] is the seam for
29//! a byte-compatible migration.
30//!
31//! # Archive format (version 1)
32//!
33//! All integers are little-endian. The single-file layout is:
34//!
35//! ```text
36//! offset 0  ARCHIVE_MAGIC ("RMOG")                        4 bytes
37//! offset 4  format version (u32)                          4 bytes
38//! offset 8  table-of-contents entry count (u32)           4 bytes
39//! offset 12 table-of-contents entries, 48 bytes each:
40//!           resource name (32 ASCII bytes, NUL-padded) +
41//!           resource offset (u64) + resource byte length (u64)
42//! resources in canonical order (see docs on [`archive`]), each offset a
43//! multiple of 8; unnamed padding gaps of up to 7 bytes may separate them.
44//! ```
45//!
46//! Resources hold packed array-of-structs records — the GraphHopper-style
47//! encoded-value columns ([`archive::EDGE_RECORD_BYTES`]'s `encoded_value`:
48//! speed cells, road class, direction access) keep the routing hot path
49//! branch-free. Corruption anywhere fails typed: [`geospatial_types`]'s
50//! `SDKError::OfflineRoutingFailure` with
51//! `OfflineGraphInvalidReason::{ArchiveMalformed, VersionUnsupported,
52//! IndexOutOfRange}`.
53//!
54//! # Slices
55//!
56//! This crate currently provides: the archive format, validator and
57//! deterministic writer ([`archive`]); the minimal OSM routing profile
58//! ([`profile`]); the compiler pipeline ([`compiler`]); and the native,
59//! memory-mapped consumption seam ([`mmap_reader`]). The
60//! `OfflineRoutingProvider` implementation (in `map-core`) and the wasm
61//! in-memory path are the remaining milestone M7 slice-2 work and consume
62//! this crate's format unchanged.
63
