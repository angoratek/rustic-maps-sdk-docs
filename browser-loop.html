Rustic Maps SDK

The browser loop (platform/web/)

Maintainer guide to the wasm browser harness: build the pkg, serve it, test it in Playwright, and understand what the WebGPU canvas is allowed to assume. Every fact below is grounded in the named files; the one forward-looking section is clearly marked (see “Canvas-vs-golden compare (designed, not yet implemented)”).

Building the pkg

The harness has no bundler and no wasm-pack; wasm-bindgen-cli runs directly (same commands as the README’s WebAssembly section):

rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129   # must match the crate version
cargo build -p map-web-bindings --release --target wasm32-unknown-unknown
wasm-bindgen --target web --out-dir platform/web/pkg \
  target/wasm32-unknown-unknown/release/map_web_bindings.wasm

Version matching is load-bearing. wasm-bindgen-cli refuses (or corrupts) mismatches against the wasm-bindgen crate version the wasm binary was compiled with. The workspace pins wasm-bindgen 0.2.129 (crates/map-web-bindings dependency tree) and the installed CLI is 0.2.129 — after any wasm-bindgen bump, reinstall the CLI at the same version and regenerate platform/web/pkg. Check both ends with wasm-bindgen --version and cargo tree -p map-web-bindings | grep wasm-bindgen.

Clippy runs for both hosts on this crate: cargo clippy -p map-web-bindings --target wasm32-unknown-unknown (the GPU canvas slice is cfg-gated to wasm32).

Contract-sync test (UDL ↔ wasm surface)

node --test platform/web/tests/contract_sync.mjs asserts the wasm surface mirrors the frozen UniFFI contract crates/map-native-core/src/ map_native_core.udl (PRD §4.7) with no npm dependency: a small line parser reads the UDL, the curated TypeScript mirror (platform/web/types/ map_native_core.d.ts) and the hand-reviewed wasm exports (crates/map-web-bindings/src/exports.rs) and compares the shared camera/projection surface. Per frozen dictionary it requires the same field names (snake_case UDL fields versus the mirror’s lower camel case, e.g. tile_x ↔ tileX) and the UniFFI types’ TypeScript spellings (double/u32 ↔ number); it then requires the frozen MapCamera methods and free helpers in the UDL and in both wasm sources, and rejects a wasm member the UDL lacks (the wasm-only lifecycle helpers start_sdk and retina_device_pixel_ratio_threshold are the documented exceptions). The comparison is addition-tolerant: contract-only members (the MapSdk provider surface, the fit_bounds constructor) are never required on wasm, so the UDL can grow without breaking the test. The generated pkg/ map_web_bindings.d.ts is checked the same way whenever the build artifact is present. No server or browser session is needed to run it, and the Playwright config’s globalSetup also runs it before every npx playwright test.

Serving and manual testing

node platform/web/serve.mjs    # http://localhost:8642/

The server answers / and static paths from platform/web/, and /tiles/{zoom}_{x}_{y}.png from the recorded platform tile fixtures (the browser never fetches an external network; unknown tiles 404). The playground camera defaults to the Zurich anchor (47.3769, 8.5417) at zoom 14 — the recorded fixture neighborhood — so the page shows real imagery immediately.

The browser never needs flags for the manual loop: plain Chrome and localhost (a secure context) resolve WebGPU.

Running Playwright e2e

cd platform/web
npx playwright install chromium   # first time only
npx playwright test               # 6 tests, chromium channel, headless

Config details that matter: deviceScaleFactor: 1 (canvas backing pixels == viewport pixels), viewport 640×480, and the config’s own webServer spins up serve.mjs with reuseExistingServer: false — the port 8642 is hardcoded, so a manually started server or another running harness will conflict (kill it or the run fails to bind; see “Known gaps”).

Tests gate on window.mapTestReady (resolves only after the Rust-side start_sdk completed) and additionally on window.mapRendererMode() for GPU-path assertions; the smoke test skips with a documented reason when the mode degrades to overlay.

WebGPU facts

  • Secure context required; localhost counts. WebGPU only exists in secure contexts, and http://localhost:8642 qualifies.
  • Chromium channel works out of the box headless (verified during the M8 canvas slice): the adapter resolves with no launch flags at all. The Playwright config still passes --enable-unsafe-webgpu --enable-gpu --use-angle=swiftshader --no-sandbox — belt-and-braces flags for GPU process stability in headless, not requirements in the current build.
  • drawImage of a WebGPU canvas reads only a freshly presented frame. Once the compositor has consumed a presented frame, later drawImage calls stop yielding those bytes. The smoke test works around this by nudging a zero-delta wheel event (re-schedules a GPU frame without moving the camera) and sampling getImageData across the following animation frames. Any future pixel probe of #map-canvas must reuse this pattern.
  • Playwright’s WebKit also resolves WebGPU today (WebKit 27.2, webkit-2370, verified headless on macOS): navigator.gpu exists, the page initializes in gpu mode and the frame statistics read requested 4 / drawn 4 / missing 0 at fetch zoom 14 with real imagery on the surface. The 2D overlay fallback is therefore not what a WebKit run exercises today; it fires only when GpuMapCanvas fails to acquire an adapter or device.

The 2D-overlay fallback story

GpuMapCanvas::initialize fails cleanly (string error, no panic) when no WebGPU adapter supports the canvas or the device request fails; the playwright page catches that, abandons the GPU canvas, and reports mode overlay (WebGPU unavailable: …) in the status line and readout. In overlay mode the separate #map-overlay canvas is the scene (background grid + projected tile grid from visible_tile_keys); in GPU mode the overlay carries only the opt-in debug tile grid and a red center mark, so the WebGPU-locked canvas never needs a 2D context of its own (claiming one would poison the surface).

Two overlapping notes on fallback breadth:

  • wgpu is compiled with both webgpu and webgl workspace features, so the wasm adapter request could in principle also reach a WebGL2 context on canvas — the canvas slice deliberately does not implement or test that path; the documented fallback is the 2D overlay.
  • The historical PLAN line “WebGL2 fallback checked in Safari/WebKit” is softened by the WebKit finding above: current WebKit ships WebGPU, so the thing to check there is graceful degradation, not WebGL.

Parity with the native renderer

crates/map-web-bindings/src/canvas.rs mirrors the native headless pipeline in crates/map-rendering (which cannot be reused directly: it is cfg-gated out on wasm) and the rule is same WGSL text, same vertex layout, same index pattern:

  • The WGSL (TILE_QUAD_SHADER_SOURCE) is copied verbatim from the native renderer: clip-space positions in, texture sample out.
  • Vertices are ClipSpaceTileVertex chunks (Float32x4 clip position at offset 0, Float32x2 texture coordinates at the offset_of! offset), the same memory layout the native map-rendering encoder emits.
  • Indices are u16 in the two-triangle pattern 0, 1, 2, 2, 1, 3 (INDICES_PER_QUAD = 6, CORNERS_PER_QUAD = 4), with the caller bounding fragments under MAXIMUM_QUADS_PER_FRAME before encoding.
  • Tile textures are Rgba8Unorm with a linear, clamp-to-edge sampler; both preferred surface formats (Bgra8Unorm, Rgba8Unorm) are non-sRGB, so tile texel values reach the screen unchanged — the parity that makes a browser-vs-golden pixel compare meaningful.
  • Degradation rules match too: an undecodable pooled payload skips its quads for the frame and is evicted from the pool for refetch, while only structural failures surface as errors.

The page must also serialize frames: the wasm binding borrows its draw state across the render_frame future, so overlapping calls are a borrow violation — the playground keeps a busy/queued render loop.

Canvas-vs-golden compare (implemented: tests/golden_compare.spec.mjs)

The two committed goldens (crates/map-rendering/fixtures/render/golden/) are rendered with the exact camera the playground defaults to — center 47.3769/8.5417, zoom 14, bearing 0, pitch 0 (pitched variant 45°), field of view 60° == map-rendering‘s DEFAULT_FIELD_OF_VIEW_DEGREES — so the only parameter to bridge is the 512×512 viewport of golden_image.rs vs the harness’ 640×480 window.

  • Probe mechanics (reuse the smoke test’s proven pattern): a zero-delta wheel nudge to re-present, then drawImage the GPU canvas into a same-size 2D probe and sample getImageData across a dozen animation frames, keeping the best (minimum-error) sample — a stale pre-presentation read is a clear-color frame and maximizes the error rather than matching.
  • Pixel geometry: set the viewport to 512×512 (or back the canvas explicitly) with deviceScaleFactor: 1, so composited pixels are 1:1 with canvas backing pixels and the sampler never rescales. The clear color [0, 0, 0, 1] and CompositeAlphaMode::Opaque make the 2D round trip opacity-neutral (premultiplication is a no-op at alpha 255).
  • Golden bytes reach the page the way tile fixtures do: an added allow-listed route in serve.mjs (e.g. /golden/{file}.png naming only the two committed goldens) keeps the compare same-origin and lets the page createImageBitmap the golden and diff in-page, avoiding a 512×512×4 payload over the Playwright protocol. A dedicated minimal fixture page (a fixed 512×512 canvas rendering the golden camera on demand) beats driving the playground UI for this test.
  • Tolerance strategy: mirror golden_image.rs verbatim — mean absolute per-channel error ≤ 2.0, and at most a 0.02 fraction of pixels whose maximum channel error exceeds 24 — plus preconditions (golden decodes to 512×512; settled frame statistics match the scene’s tile counts and tileZoomLevel === 14; the pitched camera’s fully culled 14/8579/5737 leaves one requested-but-undrawn tile, so its expected missingTiles is 1, not 0). The comparison there is pixel-loop based, not screenshot-based, which is the right granularity for the browser probe too. The page also reproduces the golden harness’s deliberate parent-fallback tile (the last visible scene tile drawn from its pooled zoom-13 parent via GpuMapCanvas::stage_tile_parent_fallback), without which the browser would draw sharper imagery than the reference.
  • Hazards: (1) the freshness rule above — probe only right after a forced re-present, never assume render_frame‘s resolution implies readable bytes; (2) canvas size mismatch — the playground resizes its canvases to the window, so the test must control the window or use a dedicated page; (3) --use-angle=swiftshader renders the software ANGLE path, whose sampler behavior is exactly the GPU-vs-GPU difference the tolerance absorbs — if the SwiftShader mean error exceeds the budget, drop the swiftshader arg for this test project rather than widening the shared tolerance; (4) the fetch zoom clamps to the fixtures’ maximum (14), so cameras above zoom 14 are not apples-to-apples against these goldens.

Known gaps

  • serve.mjs hardcodes the host/port (localhost:8642) and the Playwright config runs with reuseExistingServer: false, so two harness sessions (or a manual server plus a test run) cannot share the machine’s single port. A test-only copy with an environment-variable port override is the current workaround; upstreaming that override would be a one-line change.
  • Nothing in the repo automates the pkg step (no script wrapping the cargo build + wasm-bindgen pair documented above); regenerate by hand and commit the pkg/ output as the slice does today.
  • Playwright’s WebKit browser binary is not installed by the harness (only the chromium channel is pinned in browsers.json); enable the WebKit check with npx playwright install webkit before running it.
  • The project’s chromium tests use --use-angle=swiftshader (software GPU); a hardware-GPU compare run is untested.
